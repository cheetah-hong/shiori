# 문서 스캔 전처리 실험 — 깨끗한 페이지와 OCR 점수

- 날짜: 2026-11-05 (KST), MacBook arm64 · macOS 26.3 · Xcode 26.6 · Swift 6.3
- 사진: 교재 5장(p012, p013, p069, p157, p185). 측정은 저장소에 포함하지 않은 교재 5쪽(59단어) 비공개 세트로 했습니다.
- 채점기: 저장소의 `research/ocr/prototype/parse_eval.py`(수정하지 않음). 정답은 비공개 폴더의 `textbook/vocab_n5n3/ground_truth.json`입니다.
- 사진, 처리 이미지, 판독 결과, 점수표는 교재 본문이 들어 있어 저장소에 없습니다. 모두 비공개 폴더 `$SHIORI_PRIVATE_DIR`
  (기본 `<repo>/.private`)의 `textbook/` 아래에 있습니다. 아래에서 `out/`, `fixtures/`, `scores/`로 시작하는 경로는 비공개 폴더의 `textbook/scan/` 기준입니다.
- 기준(지금 방식): 원본 사진을 EXIF로 세우고 두 번 판독 → **줄 전체 52/59, ★ 56/59, 조용한 오류 1**
- 처리 도구: `tools/scan.swift` — Vision(`VNDetectDocumentSegmentationRequest`, `VNDetectRectanglesRequest`,
  `VNRecognizeTextRequest`)과 Core Image 내장 필터만 씁니다. 같은 API가 iOS에도 있습니다.

## 0. 결론 요약

1. **OCR에는 정리하지 않은 컬러 이미지를 넣습니다.** 회색조, 배경 고르게 하기, 이진화는 OCR 점수를 올리지 못했습니다.
   - 줄 전체: 원본 52/59 → 필터만 적용 24~43/59
   - 글자 재현율(좌표 무관): 읽기·뜻·예문은 거의 같고, 표제어는 49~54/59(보정 + 이진화만 40/59)
   - 배경을 하얗게 지우면, 색 띠 위에 있던 획이 적은 한자 표제어를 Vision이 무시합니다.
     예전에 "칸만 잘라 판독"했을 때 8/15로 나빠진 것과 같은 현상입니다.
2. **원근 보정만 해도 지금 해석기 점수는 내려갑니다.** 보정한 이미지 좌표를 그대로 쓰면 30/59, 원본 사진 좌표로 되돌리면 40/59입니다.
   해석기의 칸 위치 기준(`ax+0.17` 등)이 "원본 사진 폭"에 맞춰져 있기 때문입니다.
   페이지만 잘라 주는 스캐너를 쓰려면, Dart 해석기는 칸 위치를 내용에서 잰 길이 기준으로 바꿔야 합니다(4.5절).
3. **점수를 올린 것은 두 가지뿐입니다.**
   - ★만 따로 읽는 세 번째 판독(이진화 이미지): **54/59, ★ 58/59**. 다른 칸 변화 없음, 조용한 오류 1 그대로
   - 휜 페이지 펴기(page-dewarp)를 p157에 적용: 그 쪽만 5/6 → 6/6
4. **검토 화면용 "깨끗한 페이지"는 `c-flatcolor`를 권합니다.**
   - 처리: 원근 보정 → 컬러 ÷ 큰 반경 배경 추정치 → 레벨 조정
   - 종이는 하얗게 고르게, 그림자와 뒷면 비침은 거의 사라지고, 색 띠와 ★는 남습니다.
   - 2000px JPEG 0.5~0.8MB, Mac에서 2000px 6~10ms(원본 해상도 15~71ms)
5. **페이지 찾기는 혼자 믿을 수 없습니다.**
   - `VNDetectDocumentSegmentationRequest`가 본문 페이지만 잡은 것은 2/5(p013, p185)입니다.
     3장은 옆 페이지까지 포함했습니다(p157은 펼친 면 전체가 기울어진 사각형).
   - `VNDetectRectanglesRequest`가 맞힌 것은 1/5(p013)입니다.
   - 두 페이지 사이 접히는 부분(gutter)에는 사각형 경계선이 없어서 생기는 실패입니다. 모서리를 손으로 고치는 화면이 필요합니다.
6. **회전은 EXIF 없이 판별됩니다.**
   - Vision 판독 상자의 글 방향(topLeft→topRight) 투표가 **50/50 정답**이었습니다(5장 × 4방향 + EXIF 무시 5건, 두 해상도).
     득표율 0.88 이상이고 180°도 구분합니다.
   - 글상자 가로세로 비율은 1600px에서 25/25, 1024px에서 16/25였습니다. 옆으로 누웠는지만 알 뿐 90°와 270°, 0°와 180°를 가르지 못해 보조 신호로만 씁니다.

## 1. 처리 변형

모든 변형은 같은 원근 보정 이미지(또는 4.2절의 "펴지 않음" 실험에서는 세운 원본)에서 시작합니다. 반경은 페이지 긴 변에 대한 비율입니다.

| 변형 | 처리 | 쓰임 |
|---|---|---|
| `a-persp` | 원근 보정만 (`CIPerspectiveCorrection`) | 대조군 |
| `b-gray` | 회색조(`CIColorControls` 채도 0) + 1%/99% 대비 늘이기 | (b) |
| `c-flat` | 회색조 ÷ 배경 추정치(최대값 필터 → 흐리기, 반경 3%, 1/8 축소본에서 계산) → 레벨 0.15–0.92 | (c) 그림자 제거 |
| `c-flatcolor` | 컬러 ÷ 배경 추정치(반경 3%) → 레벨 0.08–0.94. 종이만 하얗게, 색 띠는 유지 | 검토 화면용 |
| `d-binary` | 회색조 ÷ 작은 반경(0.6%) 배경 → 0.80 기준 이진화(`CIColorThreshold`) | (d) vFlat "문서" 모드 느낌 |

- `CIDivideBlendMode`는 `배경 이미지 / 입력 이미지`를 계산합니다. 그래서 페이지를 배경 추정치로 나눌 때는 입력 자리에 배경 추정치를 넣습니다.
- 작업 색공간은 비선형 sRGB로 두었습니다. 그래서 기준값이 8비트 값처럼 읽히고, 나누기는 감마와 무관하게 같은 결과가 나옵니다.

## 3. 회전 판별 (EXIF 없이)

`scan orient`는 이미지를 긴 변 N px로 줄인 뒤 두 신호를 봅니다(`tools/orient_eval.py`, 결과는 비공개 폴더의 `scores/orientation.md`).

| 신호 | 긴 변 1600px | 긴 변 1024px | 비용(중앙값) | 180° 구분 |
|---|---|---|---|---|
| 판독 상자 글 방향 투표 (`VNRecognizeTextRequest` accurate, ja·ko) | **25/25** | **25/25** | 1600px 397ms, 1024px 345ms | 됨 |
| 글상자 가로세로 비율 중앙값 < 1.5 (`VNDetectTextRectanglesRequest`) | 25/25 | 16/25 | 약 20ms | 안 됨 |

- 시험: 5장 각각을 0°/90°/180°/270°로 돌린 20건 + EXIF를 무시한 원래 픽셀 5건
  - EXIF를 무시한 5건에는 EXIF 값이 없는 p012·p013과, EXIF=6인 나머지 3장이 모두 들어 있습니다.
- 정답 방향의 득표율은 최저 0.88, 대부분 0.97 이상입니다.
- `.fast` 판독은 일본어를 지원하지 않아 쓸 수 없습니다.
- 예전에 "OCR 점수로 방향 고르기"가 실패한 이유: Vision은 돌아간 글자도 읽으므로 점수 차이가 작습니다.
  하지만 돌려주는 상자는 글 방향대로 돌아가 있어서, 그 방향 자체가 확실한 신호가 됩니다.
- 앱 적용: 첫 일본어 판독 결과로 방향을 보고, 0°가 아닐 때만 돌려서 다시 판독합니다. 바른 사진이면 추가 비용이 없습니다.
- 책상 위 교재를 위에서 내려 찍으면 휴대폰이 방향을 모릅니다. p012·p013의 EXIF가 1(회전 없음)로 남은 이유로 보입니다.
  그래서 스캐너를 쓰더라도 이 판별은 OCR 블록에 둡니다.

- 읽기·뜻·예문은 변형과 거의 무관합니다. Vision accurate는 그림자, 기울기, 색 띠에 이미 강합니다.
- **표제어와 ★가 서로 반대로 움직입니다.**
  - 회색조·배경 고르게 하기는 ★를 더 읽습니다(보정 후 29줄). 주황 ★가 회색이 되면 바탕과 대비가 커지기 때문으로 보입니다.
  - 대신 p012의 단순한 한자 표제어를 잃습니다(쪽별 표제어 11→7~8).
- 그래서 컬러 두 번 판독은 그대로 두고, ★만 정리 이미지에서 가져오는 방법을 시험했습니다(4.4절).

### 4.4 ★ 보조 판독 (세 번째 판독에서 ★만 가져오기)
`tools/star_merge.py`: 원본 두 번 판독에, 정리 이미지(펴지 않음, 같은 좌표) 일본어 판독의 ★ 글자 위치만 더합니다.

| 조합 | 줄 전체 | ★ | 다른 칸 | 조용한 오류 |
|---|---|---|---|---|
| 원본 | 52/59 | 56/59 | — | 1 |
| 원본 + b-gray의 ★ | 52/59 | 56/59 | 같음 | 1 |
| 원본 + c-flat의 ★ | 53/59 | 57/59 | 같음 | 1 |
| **원본 + d-binary의 ★** | **54/59** | **58/59** | 같음 | 1 |

- 되찾은 ★는 2개(p013 1개, p157 1개)입니다. 남은 것은 p185의 1개입니다. 잘못 붙은 ★는 없습니다.
- 비용은 판독 한 번(약 0.4~0.5초)과 이진화 18~84ms입니다. 다만 사진 5장, ★ 누락 3개로 본 결과라 더 많은 사진으로 확인해야 합니다.

### 4.5 페이지 좌표를 한 배율로 줄이면 해석기가 되살아나는가
`tools/page_units.py`: 보정 이미지 좌표를 `0.5 + K·(v − 0.5)`로 줄여 "사진 안에서 K만큼 차지하는 페이지"처럼 만듭니다.
p013·p185처럼 바르게 잡힌 본문 페이지는 원본 사진 폭의 0.70~0.76을 차지합니다.

| 입력 | 줄 전체 | 쪽별 |
|---|---|---|
| a-persp · 페이지 좌표 그대로 | 30/59 | 012:11 013:4 069:12 157:0 185:3 |
| × 0.72 | 15/59 | 012:0 013:12 069:0 157:0 185:3 |
| × 0.80 | 36/59 | 012:11 013:12 069:10 157:0 185:3 |
| × 0.88 | 34/59 | 012:11 013:8 069:12 157:0 185:3 |
| (참고) 사진 좌표로 되돌림 | 40/59 | 012:11 013:12 069:12 157:2 185:3 |

- 상수 하나로는 모든 쪽을 맞출 수 없습니다. p013은 0.72에서 되살아나고, p012는 0.72에서 0이 됩니다.
  사진마다 잘린 범위(옆 페이지 포함 여부)가 다르기 때문입니다.
- Dart 해석기 권고: 칸 위치를 "사진 폭의 몇 %"가 아니라 **내용에서 잰 길이**로 정합니다.
  예: 번호 칸 x에서 읽기 칸 x까지의 중앙값 거리, 또는 번호 칸에서 페이지 오른쪽 끝까지의 폭.
  그래야 원본 사진, 스캐너가 자른 페이지, 펴진 페이지를 모두 같은 규칙으로 읽습니다.

### 4.6 해석기 약점 (Dart 이식 때 고칠 것, 이 실험에서는 고치지 않음)
1. 번호처럼 보이는 숫자 덩어리 하나(뜻 한 줄을 잘못 읽은 네 자리 숫자)가 옆 페이지 묶음을 만듭니다.
   → 기준점이 3개 미만이거나 체크박스 글자(`□口ロ`)가 붙지 않은 묶음은 페이지로 인정하지 않습니다.
2. 읽기 칸 조건이 "가나만"이라, ★가 읽기와 한 덩어리로 붙으면 읽기를 잃습니다.
   → `★☆*`를 먼저 떼어 내고 ★ 표시로 기록합니다.
3. 칸 위치가 사진 폭 기준입니다(4.5절).
4. 형식 판별이 "번호 간격 중앙값 > 0.08"뿐이라, 번호를 몇 개만 읽으면 A형을 B형으로 잘못 고릅니다(보정 + 이진화 p013).
   → 읽기 칸 덩어리 수, 예문 줄 유무 같은 두 번째 신호를 함께 봅니다.

## 5. 휜 페이지 펴기 (선택 과제)

- 도구: `page-dewarp` 0.1.9 (lmmx, **MIT**). mzucker/page_dewarp를 Python 3으로 옮긴 것입니다.
  - 최신판은 0.3.4(2026-05-12, Python 3.10+, JAX 선택)입니다. 이 Mac의 Python이 3.9라 pip가 0.1.9를 골랐습니다.
  - 의존: numpy, scipy, opencv-python, sympy, matplotlib, msgspec. `research/scan/.venv`에만 설치했습니다(.gitignore).
  - 이 패키지는 Python 3.10 문법을 씁니다. 그래서 `.venv` 안의 복사본만 3.9에서 돌도록 고쳤습니다(`match` 1곳 → `isinstance`, `from __future__ import annotations` 추가).
- 방식: 순수 기하입니다. 글줄 윤곽 찾기 → 글줄 묶음 → 3차 곡면 + 카메라 자세를 `scipy.optimize`(Powell)로 맞춤 → `cv2.remap`
  - 학습 모델이 없어 모델 파일이 필요 없습니다.
- 속도(Mac, Python): 한 장 1.1~4.0초. 출력은 회색조 PNG(`-nb 1`)입니다.
- 결과
  - p157(가장 많이 휜 쪽): 휜 줄이 거의 곧게 펴졌습니다. 그 쪽 줄 전체가 5/6 → **6/6**(★ 하나 회복)입니다. 다른 4쪽은 원본 판독을 써서 합계 53/59입니다(비공개 폴더의 `scores/dewarp-page.txt`).
  - 5장 모두 펴면 글자 재현율은 비슷하거나 낫습니다(★ 30줄, 표제어 54/59). 하지만 해석 점수는 24/59로 떨어집니다(비공개 폴더의 `scores/dewarp-all.txt`).
    펴진 이미지는 페이지 크기에 맞춰 잘려 좌표 축척이 바뀌기 때문입니다(4.5절과 같은 원인).
  - 원근 보정본(p157 a-persp)에 돌리면 오른쪽 DAY 탭 부분이 잘렸습니다. 원본 사진에 돌리는 편이 낫습니다.
- 앱 적용 가능성: Dart만으로 옮기기는 어렵습니다.
  - 적응형 이진화, 윤곽 찾기, remap은 OpenCV가 필요합니다(`opencv_dart` 또는 네이티브 OpenCV).
  - 최적화기(Powell)는 직접 옮기거나 다른 최적화기로 바꿔야 합니다.
  - iOS는 Core Image(`CIFilter` 사용자 커널 또는 Metal)로 remap 할 수 있지만, 곡면 맞추기는 직접 구현해야 합니다.
  - **첫 버전에서는 넣지 않습니다.** 휜 쪽이 많다는 사용자 보고가 쌓이면 다시 봅니다.
  - 그때는 학습 모델 UVDoc(MIT, 약 30MB)도 비교합니다. 작은 격자만 추론하고 원본 해상도에 적용해 컬러가 보존되고, ONNX → CoreML/TFLite 경로가 있습니다(`LIBRARIES.md` 3절, 시험 안 함).
- 이미지(비공개 폴더): `out/dewarp/_sheet.jpg`(원본 → 펴기, 보정본 → 펴기)

### 7.1 결론
- **`ImageSource` 첫 어댑터: 일반 촬영·앨범 사진(정리하지 않은 컬러 원본).** 측정한 52/59가 이 구성입니다.
  - 지금 해석기는 사진 좌표 기준이라, 스캐너가 페이지만 잘라 주면 30/59로 떨어집니다(4.1절).
  - 스캐너의 페이지 찾기도 펼친 책에서 3/5 실패했습니다(2절, 같은 Vision 분할 기준).
  - 정리 필터는 OCR에 도움이 되지 않습니다(4.2절).
    그런데 iOS `VNDocumentCameraViewController`는 필터를 끌 수 없고, `flutter_doc_scanner`는 Android가 FULL 모드로 고정입니다(`LIBRARIES.md`).
- **두 번째 어댑터(해석기를 내용 기준 단위로 바꾼 뒤, 4.5절)**
  - Android: `cunning_document_scanner` 3.0.4(MIT) + `AndroidScannerMode.base`
    - ML Kit Document Scanner BASE 모드: 필터 없이 컬러 유지, 모서리 고치기 화면과 여러 장 촬영 포함
    - Play 서비스가 없으면 내장 수동 크롭으로 넘어갑니다.
  - iOS: VisionKit 카메라 대신 **직접 구현**(촬영 → `VNDetectDocumentSegmentationRequest` → 모서리 조정 → `CIPerspectiveCorrection`)
    - `scan.swift`의 `detectSegmentation`·`rectify`와 같은 호출이고, OpenCV가 필요 없습니다.
    - cunning의 iOS 갤러리 경로도 같은 구성(`IosDocumentFilter.original`)이지만, 긴 변을 2048px로 줄이고 모서리를 돌려주지 않습니다.
  - 두 어댑터 모두 같은 `ImageSource` 포트 뒤에 두어 첫 어댑터와 바꿔 끼울 수 있게 합니다.
- **OCR 블록에 넣을 것** (어떤 어댑터를 쓰든)
  1. 회전 판별: 첫 일본어 판독의 상자 방향 투표 → 0°가 아니면 돌려서 다시 판독
     - 위에서 내려 찍은 사진은 EXIF가 비고(p012·p013), ML Kit은 자동 회전을 끌 수 없는데 180° 오판 보고(#843)가 있습니다.
  2. ★ 보조 판독(선택): 이진화 이미지로 일본어를 한 번 더 읽어 ★ 위치만 더함(+2줄, 0.5초)
- **앱에서 직접 할 정리: 검토 화면 표시용 `c-flatcolor` 하나만.** OCR 입력은 바꾸지 않습니다.
  - iOS: `scan.swift`의 `detectSegmentation` → `rectify` → `background`/`divide`/`levels`를 그대로 옮길 수 있습니다(Vision + Core Image).
  - Android: Core Image가 없으므로 OpenCV(`warpPerspective`, 최대값 필터, 나누기)로 같은 식을 구현하거나, 첫 버전에서는 세운 원본을 보여 줍니다.
  - 페이지 사각형은 자동으로 잡고, 사용자가 모서리를 고칠 수 있게 합니다(분할 성공률 2/5).
  - 표시용 이미지는 OCR 결과로 다시 자를 수 있습니다. 본문 페이지의 번호 칸(기준점) 묶음 x 범위 + 여백으로 옆 페이지 조각을 잘라 냅니다.
- **하지 않을 것:** OCR 입력의 회색조, 대비 조정, 배경 고르게 하기, 이진화. 첫 버전에서는 휜 페이지 펴기도 하지 않습니다.
  - 나중에 넣는다면 UVDoc(MIT, 약 30MB, ONNX → CoreML/TFLite, 컬러 보존)이 page-dewarp보다 옮기기 쉽습니다(`LIBRARIES.md` 3절).

## 8. 남은 문제
- 펼친 책에서 본문 페이지만 자동으로 고르는 방법이 없습니다. 모서리 고치기 화면이나, OCR 기준점으로 다시 자르기가 필요합니다.
- 해석기 약점 3가지(4.6절)는 앱의 Dart 해석기에서 고쳐야 합니다.
- ★ 보조 판독과 휜 페이지 펴기는 사진 5장으로만 확인했습니다. 그림자가 심하거나 흐린 사진, 다른 DAY를 더 모아야 합니다.
- Android(ML Kit)에서는 측정하지 않았습니다. 회전 판별의 "상자 방향" 신호가 ML Kit에도 있는지(`cornerPoints`) 확인해야 합니다.
- 시간은 Mac 기준입니다. iPhone 13 mini 같은 실기기 측정이 필요합니다.
- Swift 도구(`scan.swift`)에는 자동 단위 테스트가 없습니다. 회전 판별은 50건 통합 시험(`orient_eval.py`)으로, 페이지 찾기·보정은 비교 이미지로만 확인했습니다.
  앱으로 옮길 때 XCTest(투표 함수, 사각형 고르기, 배경 나누기 식)를 붙여야 합니다.
- VisionKit 스캐너의 기본 필터(Color로 추정)와 ML Kit BASE 결과의 해상도·OCR 점수는 기기에서 재야 합니다.
- iOS 26 `RecognizeDocumentsRequest`(표·목록 구조)는 목록형(A형) 해석에 도움이 될 수 있지만 시험하지 않았습니다. CJK는 단어 단위 결과를 지원하지 않습니다.
