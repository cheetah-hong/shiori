# 일본어 TTS 악센트 실험 — 정답 데이터 + 직접 지정

- 날짜: 2026-11-05 (KST), MacBook arm64(Apple M5, 10코어) · macOS 26.3.1 · Python 3.11
- 질문: 단어와 예문을 도쿄 표준어 高低 악센트로 들려줄 수 있는가. 사람이 귀로 판단하지 않고 기계로 확인한다.
- 방법 한 줄: 악센트 정답 데이터(UniDic `aType`, Kanjium)를 기대값과 대조하고, VOICEVOX core에 "그냥 텍스트(기본 추정)"와 "정답 악센트를 지정"을 넣어
  엔진의 악센트 값, 모라별 pitch, 실제 소리의 F0를 각각 정답과 대조했다. 기준선은 macOS `say -v Kyoko`.
- 단어·예문은 이 실험을 위해 새로 고른 일반어와 새로 지은 문장이다(`words.tsv` 28행, `sentences.tsv` 7문장).
- 소리 파일, 모델, 사전, 결과 JSON은 저장소에 없다. `.cache/`(git 제외)와 비공개 폴더 `$SHIORI_PRIVATE_DIR/tts/`(기본 `<repo>/.private/tts/`)에 있다.

## 0. 결론 요약

1. **정답 데이터는 믿을 만하다.** 값이 있는 단어에서 기대값과 다른 값은 0건이었다.
   - Kanjium: 26/26 일치(28개 중 2개 없음: お忙しい, 食べました — 활용형·접두사형이라 표제어가 아님)
   - UniDic 3.1.0과 2.1.2(lite): 21/21 일치(7개는 한 토큰 값이 없음: 복합어·활용형·조수사). 2개는 값이 여러 개(橋 2,1 · 昨日 2,0)
2. **VOICEVOX의 기본 추정(엔진 악센트 값)은 단어 25/28(89%), 예문 악센트구 16/19(84%), 문장 전체 5/7(71%).**
   - 틀린 곳: 三本(2, 정답 1), 日本을 にっぽん으로 읽음, 一日을 늘 いちにち로 읽음, 예문 속 電話番号を(6, 정답 4), 降っています를 두 구로 나눔
   - pyopenjtalk의 텍스트→악센트 추정은 VOICEVOX 기본과 **28/28 단어, 7/7 문장에서 똑같았다**(같은 Open JTalk 계열 사전·규칙).
3. **정답을 직접 지정하면 엔진 악센트 값은 단어 28/28(가나 지정·사용자 사전 모두), 예문 악센트구 17/19(사용자 사전)로 올랐다.**
   구 편집(17/17)은 기대값을 `accent`에 직접 넣는 방식이라 값 일치는 구조상 당연하다. 그 경우의 근거는 4·5절의 pitch·F0 측정이다.
   읽기 지정(가나 입력) 또는 사용자 사전으로 一日=ついたち, 日本=にほん 같은 읽기 문제도 함께 고쳐진다.
4. **엔진이 받은 악센트대로 소리가 나는지도 확인했다.**
   - 합성한 소리의 F0를 다시 재면, 쿼리의 모라 사이 오르내림 방향과 **210/210(100%) 같았다**(변화 0.05 이상인 곳).
   - 최소쌍(箸·橋·端 등)에서 형에 따른 차이가 정해진 방향으로 나는지 보는 대비 검사는 **3개 음성 24/24 통과**.
5. **다만 모라 단위 高低를 교과서 표기 그대로 읽으면 일치율이 낮다(지정 35~43%).** 하강이 한 박 늦게 나타나기 때문이다.
   - 두고형(1)은 24/24가 "둘째 박이 가장 높고 셋째 박에서 내려가는" 모양(LHL로 읽힘), 중고형도 24/27이 한 박 늦다.
   - 실제 도쿄 발화에서도 하강이 핵 다음 박에서 일어나는 「遅下がり」가 알려져 있어, 엔진의 결함이라기보다 측정 규칙의 한계로 본다(4.3절). 단, 귀로 확인한 결과는 아니다.
   - **미고형(2박+조사)의 일부는 실제로 구별이 약하다.** 紙が·髪が는 3개 음성 모두 조사에서 내려가지 않아(둘째 박→조사 +0.00~+0.03) 평판형과 거의 같게 들릴 수 있다. 橋が는 내려간다(−0.08~−0.11).
6. **Kyoko(macOS)는 악센트를 지정할 수 없고, 같은 읽기의 단어를 같은 소리로 낸다.** 箸と端의 F0가 완전히 같았다(하나는 틀린 셈). 대략 판독 일치는 12/28, 문장 끝 하강의 영향을 빼도 18/28.
7. **권장안(확신 중간):** 앱 단어장에는 Kanjium 악센트를 단어별로 싣고, VOICEVOX core를 기기에서 돌리되 **단어는 읽기+악센트를 직접 지정**해 합성한다.
   예문은 엔진 기본 추정 위에 단어장 단어만 사용자 사전으로 고정한다. 크기(모델 1개 약 59MB + Open JTalk 사전 약 102MB)와 Flutter 연결이 가장 큰 비용이다(6~7절).

### 1.1 VOICEVOX 약관 요지 (내려받기 때 동의 절차가 있다)
- 음성 모델·ONNX Runtime: 상업·비상업 모두 가능, **앱에 넣어 재배포 가능**. 생성한 음성은 각 캐릭터 규약을 따른다.
  금지: 역컴파일·리버스 엔지니어링과 그 방법 공개, 제작자·제3자에게 불이익을 주는 행위, 공서양속 위반. **VOICEVOX를 썼다는 크레딧이 필요하다.**
- 캐릭터별 크레딧은 「VOICEVOX:캐릭터명」(예: 「VOICEVOX:四国めたん」, 「VOICEVOX:ずんだもん」, 「VOICEVOX:春日部つむぎ」).
- **사전 확인·문의가 필요한 캐릭터**(이번 실험에서 쓰지 않았다): 青山龍星·もち子さん·後鬼(기업이 관여하면), No.7·ユーレイちゃん·ぞん子(상업 이용이면), Voidoll(법인 이용이면).
- 이번에 쓴 음성: 四国めたん(주 음성, 스타일 2), ずんだもん(3), 春日部つむぎ(8). 모두 크레딧만으로 이용 가능.
  같은 `0.vvm`에 든 雨晴はう(10)는 함께 받은 약관 글에 항목이 없어 쓰지 않았다.
- 앱 화면이나 정보 화면에 「VOICEVOX:四国めたん」 같은 크레딧, Kanjium 표기 문구, UniDic을 쓰면 그 라이선스 표기를 넣어야 한다.

## 2. 방법

### 2.1 단어와 기대값
- `words.tsv`: 동음 최소쌍 12개(箸1·橋2·端0, 雨1·飴0, 牡蠣1·柿0, 神1·紙2·髪2, 酒0·鮭1)와 어려운 경우 16개.
  숫자는 도쿄 악센트의 하강 위치(0=평판, n=n번째 박 뒤에서 내려감)다. 값이 둘인 단어(一日=ついたち 4/0, 昨日 2/0)는 둘 다 정답으로 본다.
- お忙しい(5)와 食べました(3)는 사전 표제어가 아니라 규칙(형용사 핵 유지, ます형은 ま 뒤 하강)으로 정한 값이다.
- 단어는 「단어+が」로 읽힌다. 조사가 있어야 평판형(端が LHH)과 미고형(橋が LHL)이 갈린다.

### 2.2 데이터 대조 (`tools/lookup_data.py`)
- UniDic: MeCab(fugashi)으로 표기를 분석해 상위 10개 분석 중 "한 토큰이고 읽기가 기대 읽기와 같은 것"의 `aType`을 모은다.
  여러 토큰으로 나뉘면 단독 값이 없음으로 센다(토큰별 `aType`·`aConType`은 결과 JSON에 남긴다).
- Kanjium: (표기, 읽기)가 정확히 같은 행. `(副)1,(名)0` 같은 품사 표시는 떼고 숫자만 쓴다.
- 판정(`tools/compare.py`): 값 하나가 기대값과 같으면 「일치」, 값이 여러 개이고 하나라도 맞으면 「일치(복수)」, 아니면 「불일치」, 값이 없으면 「없음」.

### 2.3 VOICEVOX (`tools/run_voicevox.py`)
| 경우 | 넣는 것 | 쓰는 API |
|---|---|---|
| 기본 | 텍스트 「箸が」 | `create_audio_query` |
| 지정(가나) | 읽기와 악센트를 함께 지정한 AquesTalk 풍 표기 「ハ'シガ」(평판은 마지막 박 뒤에 `'`) | `create_audio_query_from_kana` |
| 지정(사전) | 사용자 사전에 표기·발음(가타카나)·`accent_type`·품사, 우선도 10 → 텍스트 「箸が」 | `UserDict` + `OpenJtalk.use_user_dict` |
| 지정(구 편집, 예문) | 기본 추정의 악센트구 나눔이 기대와 같으면 각 구의 `accent`를 기대값으로 바꾸고 pitch를 다시 예측 | `replace_mora_pitch` |

- 엔진 악센트 값: VOICEVOX는 평판 구를 `accent = 구의 모라 수`로 적는다. 이것을 0으로 바꿔 기대값과 비교한다. 읽기가 다르면 값이 같아도 불일치로 센다.
- 모라 pitch 판독(`tools/pitch.py`, 단위 테스트 T3): pitch는 log F0(Hz)이고 무성 모라는 0이다.
  1. 구 안쪽의 무성 모라는 앞뒤 값으로 선형 보간하고, 구 양 끝의 무성 모라는 판정하지 않는다(`?`).
  2. 다음 모라보다 0.05 이상(약 5%, 0.9반음) 높은 **첫 모라**를 핵으로 본다. 그런 곳이 없으면 평판.
  3. 문턱 근거: 말소리 F0 변화를 알아듣는 차이가 대략 0.5~1반음이다. VOICEVOX 출력에서 높은 구간 안의 완만한 하강은 대부분 0.05보다 작고 악센트 하강은 0.1 이상이었다.
     최적값을 찾은 것은 아니다.
  4. 첫 음절이 무거운 단어(둘째 박이 ん·っ·장음, 이번 목록에서는 三本·日本(にっぽん)·今日·先生·電話番号)는 첫 박이 낮아지지 않는 일이 흔해 첫 박은 판정하지 않는다(악센트 사전 해설의 「初頭の低さ」 관련 주의).
- 소리 F0 재측정: 주 음성으로 합성한 WAV를 Praat(parselmouth, 5ms 간격, 75~600Hz)로 재고, 쿼리의 모라 길이로 각 모라 모음 구간을 잘라 유성 프레임의 중앙값을 쓴다.
  같은 판독 규칙으로 패턴을 만들고, 모라 사이 오르내림 방향을 쿼리와 비교한다.
- 최소쌍 대비 검사(`tools/make_report.py`): 하강 위치에 기대지 않는 두 가지 순서 관계.
  (a) 두고형 단어는 같은 읽기의 다른 형보다 "첫 박과 최고점의 차이"가 작다(처음부터 높다).
  (b) 평판 端が는 미고 橋が보다 조사 박이 더 올라간다.
- 음성: 四国めたん·ずんだもん·春日部つむぎ의 ノーマル 3개. 표의 값은 주 음성(四国めたん) 기준이고 "3 음성"이라고 쓴 수치는 셋을 모두 센 것이다.

### 2.4 Kyoko (`tools/run_kyoko.py`)
- `say -v Kyoko`로 「단어+が」를 만들고 F0의 유성 구간(처음~마지막 유성 프레임)을 모라 수로 똑같이 나눠 각 조각의 중앙값을 같은 규칙으로 읽는다.
- **대략적인 방법이다.** 모라 길이가 다르고 무성 모라가 경계를 밀며, 문장 끝 하강이 마지막 박을 끌어내린다. 그래서 마지막 박을 뺀 일치도 함께 적는다.
- iOS의 기본 일본어 음성과 같은 계열로 본다. 악센트를 지정할 공식 수단은 없다.

### 2.5 pyopenjtalk (`tools/run_openjtalk.py`)
- 소리 없이 텍스트→악센트 추정만 본다. NJD 결과에서 `chain_flag`가 1이 아닌 노드부터 새 악센트구, 그 노드의 `acc`가 구의 악센트, `mora_size` 합이 구 길이다.
- marine(딥러닝 악센트 추정)은 PyTorch가 필요해 이번에는 돌리지 않았다.

### 3.2 데이터와 기대값의 차이
- 값이 다른 경우는 없었다. 차이는 **값이 없음**과 **값이 여러 개**뿐이다.
- UniDic은 一日(いちにち)·二日·三本·図書館·電話番号를 여러 토큰으로 나눈다. 토큰의 결합형을 손으로 읽으면 기대값이 나온다.
  - 図書(1)+館(C3: 앞말 끝 박에 핵) → としょ'かん = 2
  - 電話(0)+番号(C2: 뒷말 첫 박에 핵) → でんわば'んごう = 4
  - 二(2)+日(C4: 평판화) → 0
  - 三(0)+本(C3: 앞말 끝 박, 그 박이 ん이라 앞 박으로) → さ'んぼん = 1
  - 이 결합 계산은 이번 도구에 넣지 않았다. 엔진(Open JTalk)이 같은 일을 하고, 바로 그 계산에서 三本이 틀렸다.
- UniDic은 一日 한 토큰을 ついたち로만 갖고 있다. いちにち는 一(イチ)+日(ニチ)로 나뉜다.
- 橋는 UniDic에 2와 1이 함께 있다. 정답 2가 포함되지만 데이터만 보고 하나를 고르면 틀릴 수 있다.

### 4.2 지정 결과
- 가나 지정과 사용자 사전 모두 단어 28/28. 가나 지정의 일치는 넣은 표기를 엔진이 그대로 받아들였다는 뜻이고,
  사용자 사전 쪽은 엔진의 형태소 분석이 사전 항목을 실제로 골랐는지까지 확인한 것이다. 사용자 사전은 표기 단위라 一日 하나에 ついたち와 いちにち를 동시에 줄 수 없다(한 사전 안에서 둘 중 하나).
- 예문: 사용자 사전으로 電話番号を가 4로 고쳐져 악센트구 17/19, 문장 6/7. 구 편집은 구 나눔이 같은 6문장에서 17/17.
- 가나 입력 쿼리에는 무성화 표시가 없다. 食べました의 し가 텍스트 입력 쿼리에서는 무성(pitch 0)인데 가나 입력 쿼리에서는 pitch 값이 들어갔다.
  다만 실제 소리에서는 두 경우 모두 し 구간에 유성 프레임이 없었다. 소리 차이는 작지만, pitch 판독은 이 차이로 한 박 달라졌다(LHHLLL ↔ LHHHLL).

### 4.3 모라 pitch의 한 박 늦은 하강

| 형(지정·가나, 3 음성) | 지정한 핵과 같음 | 한 박 늦음 | 그 밖 |
|---|---|---|---|
| 평판 | 17 | 0 | 1 (学生, ずんだもん: 마지막 조사 박이 0.08 내려감) |
| 두고(1) | 0 | 24 | 0 |
| 중고 | 3 | 24 | 0 |
| 미고(2박+が 등) | 9 | 0 | 6 (紙·髪: 하강 없음) |

- 예: 箸が(1)의 pitch는 5.90 → 5.99 → 5.78, 橋が(2)는 5.67 → 5.99 → 5.88. 둘 다 둘째 박이 가장 높지만,
  箸が는 첫 박이 이미 높고(차이 0.09) 셋째 박에서 크게 내려가며, 橋が는 첫 박이 낮다(차이 0.32).
- 실제 소리 F0에서도 같다(箸が: は 약 380Hz, し 418→375Hz로 떨어지며, が 330Hz).
- 실제 도쿄 발화에서도 하강이 핵 다음 박에서 실현되는 「遅下がり」(杉藤 1980)가 알려져 있다. 이번 결과는 VOICEVOX가 사람 녹음에서 배운 이 모양을 내는 것으로 보인다.
  인용은 2차 자료 요약을 통해 확인했고 원문은 열람하지 못했다.
- 그래서 "모라마다 H/L을 읽어 교과서 표기와 맞추기"는 이 엔진의 정답 여부를 재는 자로는 부적절했다. 대신 아래 둘을 근거로 삼는다.
  - 엔진 악센트 값(엔진이 그 형으로 말하려 한다는 것)
  - 최소쌍 대비 검사(형이 바뀌면 정해진 방향으로 소리가 바뀐다는 것): 3 음성 24/24
- 이 판단은 기계 측정만으로 한 것이다. 일본어 화자가 들어서 확인한 것은 아니다.

### 4.4 소리 F0 재측정
- 쿼리 pitch로 읽은 패턴과 소리 F0로 읽은 패턴: 83/93 구 일치(89%). 다른 10건 중 9건은 문턱(0.05) 근처의 작은 변화(쿼리와 소리의 차이 0.01~0.05)로
  하강 위치가 한 박 달라진 것이고(先生·日本·三本·電話番号を 등), 1건은 二日의 둘째 박이 소리에서 무성이 된 것이다. 오르내림 방향이 반대인 곳은 없었다.
- 모라 사이 오르내림 방향: 쿼리 변화가 0.05 이상인 210곳 모두 소리도 같은 방향(100%).
- 즉 "쿼리가 의도한 높낮이"와 "실제 소리"는 같은 방향이다.

### 4.5 Kyoko
- 箸と端, 紙と髪의 F0가 소수점 셋째 자리까지 같았다. 같은 읽기면 한자와 관계없이 같은 악센트로 읽는 것으로 보인다(紙·髪은 정답도 같다).
- 평판형은 문장 끝 하강 때문에 끝이 내려가 LHL로 읽혔다. 마지막 박을 빼면 18/28.
- 최소쌍 대비 검사 7/8(箸 vs 端에서 실패).

| pub.dev `voicevox_core` (비공식, MIT) | 1.2.0, 2026-11-05 갱신, 순수 Dart FFI. 대응 core 판본은 README에 명시가 약하다. 좋아요 2, 30일 내려받기 5 |
| pub.dev `voicevox_flutter` (비공식, MIT) | 0.1.1, 2026-07-25 이후 갱신 없음. iOS·Android·macOS 플러그인, 모델을 실행 중 내려받고 캐릭터 약관 동의를 받는 구조. 좋아요 0 |

- 비공식 래퍼 둘 다 사용자가 거의 없다. 쓰더라도 포크해 판본을 고정하거나, 필요한 함수(쿼리 생성·가나 쿼리·사용자 사전·합성)만 직접 FFI로 묶는 쪽을 권한다.

### 6.4 클라우드 TTS의 지정 문법 (호출하지 않음, 공식 문서만 확인)
| 서비스 | 지정 수단 | 표기 |
|---|---|---|
| Google Cloud TTS | SSML `<phoneme alphabet="yomigana" ph="…">` | 구 시작 `^`, 하강 위치 `!`(문서 설명). 이 규칙대로 쓰면 箸 `^は!し`, 橋 `^はし!`가 된다(문서에 이 예문은 없다). 어느 음성 등급에서 되는지는 문서에 없다 |

## 7. 앱에 넣는다면 — 권장안과 남는 위험

### 7.1 권장안 (확신: 중간)
1. **악센트 데이터:** Kanjium `accents.txt`에서 단어장(JMdict) 표제어와 (표기, 읽기)가 맞는 값을 뽑아 사전 asset에 함께 싣는다(+1MB 미만).
   값이 여러 개면 첫 값을 쓰되 화면에는 모두 보여 준다. 값이 없으면(활용형·접두사형) 엔진 추정에 맡기고 "추정"으로 표시한다.
   CC BY-SA 4.0이므로 이 파생 데이터도 같은 라이선스로 표시한다.
2. **단어 소리:** VOICEVOX core를 기기에서 돌리고, 읽기와 악센트를 함께 지정한다(가나 쿼리, 또는 사용자 사전 + 텍스트).
   이번 실험에서 엔진 악센트 값 28/28, 최소쌍 대비 24/24였다.
3. **예문 소리:** 텍스트로 넣되, 단어장 단어를 사용자 사전으로 고정한다(예문 악센트구 16/19 → 17/19).
   구 나눔·문맥 의존 읽기는 남는다.
4. **음성 하나만:** 四国めたん 또는 ずんだもん처럼 크레딧만으로 쓸 수 있는 캐릭터 하나를 고르고 vvm 하나만 넣는다. 크레딧 「VOICEVOX:캐릭터명」을 앱에 표시한다.
5. **캐시:** 처음 들을 때 합성해 파일로 저장한다. 미리 전부 만들어 asset으로 넣으면 단어당 수십 KB × 단어 수가 되므로 하지 않는다.
6. **iOS 기본 음성은 악센트용으로 쓰지 않는다.** 지정 수단이 없고, 같은 읽기의 단어를 같은 악센트로 낸다.

### 7.2 남는 위험
- **귀로 확인하지 않았다.** 기계 측정은 "엔진이 지정한 형으로 말하려 하고, 형이 바뀌면 정해진 방향으로 소리가 바뀐다"까지 보였다.
  한 박 늦은 하강이 도쿄 화자에게 정상으로 들리는지는 일본어 화자 몇 명의 청취 확인이 필요하다.
- **미고형의 약한 구별:** 紙が·髪が처럼 조사에서 내려가지 않는 경우가 있다. 모라 pitch를 직접 고치는(조사 pitch를 낮추는) 후처리로 보완할 수 있으나 시험하지 않았다.
- **크기:** 기기 약 170MB. 첫 실행 후 내려받기(약 90MB)로 줄일 수 있지만 내려받기·저장 관리가 생긴다.
- **읽기 변환:** JMdict 읽기(きょう)를 발음형(キョオ)으로 바꾸는 규칙이 필요하다. 이번 단순 규칙(おう→オオ, えい→エエ)은 형태소 경계에서 틀린다(思う).
- **Flutter 바인딩:** 공식 Dart 패키지가 없다. 직접 FFI로 묶는 비용과 판본 갱신 부담이 있다.
- **약관:** 캐릭터마다 다르고 바뀔 수 있다. 출시 전에 고른 캐릭터의 최신 약관을 다시 확인해야 한다.
- **문맥 의존:** 一日(いちにち/ついたち), 日本(にほん/にっぽん)처럼 문맥으로 읽기가 갈리는 단어는 단어 소리에서는 지정으로 해결되지만 예문에서는 엔진 추정에 남는다.

## 8. 실행 방법

준비(한 번):
```bash
cd research/tts
/opt/homebrew/bin/python3.11 -m venv .cache/venv
.cache/venv/bin/pip install <VOICEVOX core 0.17.1 macOS arm64 휠> praat-parselmouth pyopenjtalk fugashi unidic-lite unidic numpy
.cache/venv/bin/python -m unidic download
# VOICEVOX 내려받기 도구(릴리스의 download-osx-arm64): 약관 동의 후 ONNX Runtime·모델 0.vvm·Open JTalk 사전
# (공개 릴리스만 읽으므로 토큰은 필요 없다. 호출 한도에 걸리면 권한 없는 토큰만 GH_TOKEN으로 준다)
.cache/download-osx-arm64 --exclude c-api additional-libraries --models-pattern '0.vvm' -o .cache/voicevox_core
# Kanjium 악센트 원본 파일을 .cache/kanjium/accents.txt 로 받는다
```

실행(`research/tts`에서):
```bash
(cd tools && python3 -m unittest test_accent -v)                                     # 단위 테스트(엔진·네트워크 없이)
PYTHONPATH=tools .cache/venv/bin/python tools/lookup_data.py --kanjium .cache/kanjium/accents.txt --out .cache/results/data.json
PYTHONPATH=tools .cache/venv/bin/python tools/run_voicevox.py --core .cache/voicevox_core --audio-dir "${SHIORI_PRIVATE_DIR:-../../.private}/tts/wav" --out .cache/results/voicevox.json
PYTHONPATH=tools .cache/venv/bin/python tools/run_kyoko.py --audio-dir "${SHIORI_PRIVATE_DIR:-../../.private}/tts/wav" --out .cache/results/kyoko.json
PYTHONPATH=tools .cache/venv/bin/python tools/run_openjtalk.py --out .cache/results/openjtalk.json
PYTHONPATH=tools .cache/venv/bin/python tools/bench_voicevox.py --core .cache/voicevox_core --threads 0   # 1, 2도
PYTHONPATH=tools .cache/venv/bin/python tools/make_report.py --results .cache/results --audio-dir "${SHIORI_PRIVATE_DIR:-../../.private}/tts/wav" --out .cache/results/report.md
```
- `make_report.py`는 이 README의 표와 숫자(6.2절 속도 표 제외)를 만들고, 소리 폴더에 듣기 목록 `index.html`을 쓴다(로컬 전용).
  `make_report.py`의 속도 절은 실험 실행 1회의 평균이라 참고용이다. 6.2절 속도 표는 `bench_voicevox.py`(5회 중앙값)의 출력이다.
